### 1. GitHub Copilot ハーネスの開発者環境とトライアル環境が本日から従量課金に入った — 「作って試すだけなら無料」が終わった

**要点** 開発者環境・トライアル環境の GitHub Copilot ハーネスが本日 9/1 から Copilot Credits を消費する。ビルド前提が「公開したら課金」から「作り始めた瞬間から課金」へ変わり、PoC 用の Dev 環境をコスト見積りの外に置いていた組織は前提を引き直す必要がある。

**詳細** 一次は 8/28 付で新設された Learn ページ `power-platform/admin/manage-usage-github-copilot-harness`（`ms.date` 2026-08-28 / `updated_at` **2026-08-29T01:04Z**）で、末尾の「Prepare for the end of preview billing」節が「Developer environments and trial environments move to usage-based billing September 1, 2026」と本日を発効日として明記する。全 digest を grep したところ本ページの掲載歴はゼロだった。同ページは Copilot Credits を消費する機能とライセンス関係を表で整理している。

- 標準ハーネスのエージェント: Microsoft 365 チャネル内では M365 Copilot ライセンスでカバーされ、無ライセンスユーザーまたは M365 外チャネルでのみ課金
- ワークフローとプロンプト: ライセンスユーザーが標準ハーネスのエージェント内で実行する場合のみカバー。それ以外は課金
- コンピューター使用（CUA）: カバー対象外で全利用が課金
- GitHub Copilot ハーネスのエージェント: カバー対象外で全利用が課金。**作成時のアクティビティも実行時と同じく課金される**

管理者向けの統制も同ページに集約された。環境への前払いクレジット割当、テナントプールからの引き当てオフ（`Draw from the available capacity in my tenant`）、エージェント単位の月次上限（通知＋`Stop usage`）、環境グループの `Cost controls - Draw from tenant credit pool` ルール、Power Platform API による一括割当、PAYG 環境の Azure 予算・アラートの6経路である。⚠️ **環境への割当は境界にならない**——テナント容量からの引き当てか PAYG 課金が生きていれば、割当を超えても消費は続く。⚠️ **Azure の予算とアラートは通知するだけで Copilot Studio の消費を止めない**ため、実際の停止点はエージェント単位の `Stop usage` だけである。あわせて PPAC のエージェントインベントリに **Harness 列**（`GitHub Copilot` / `Standard` / `Copilot Chat`）が入り、課金対象エージェントを絞り込めるようになった（現時点では UI 列のみで、プログラム照会は inventory のサンプルクエリ経由）。本日以前の消費は **Manage Agents の `Non-billed Copilot Credits`** とダウンロード可能な消費レポートで方向感だけ確認できるが、Microsoft は請求見積りでも将来コストの保証でもないと明記している。⚠️ **Message Center 側の一次は読めていない**——「Copilot Studio - Billing for GitHub Copilot harness built agents begins September 1, 2026」という MC が存在することは検索索引で確認できるが、`mc.merill.net` と `m365admin.handsontek.net` はどちらもゲートウェイ拒否である。二次が伝える「8/3 より前に作成されたエージェント／ワークフローも 9/1 から対象」というスコープは一次未確認とする。⚠️ **USD 単価は本日も Learn 側に存在しない**（B-022 継続）ため、二次が挙げるクレジット単価はダイジェストに採らない。

### 2. SharePoint のクラシックページが2段階で読み取り専用になる — 退役理由に Copilot のグラウンディング精度が明記された

**要点** クラシックページと custom scripting の退役が 2027-03-01 と 2028-10-01 の2段階で告知された。前提の変化は日程より理由の側にあり、Microsoft は「クラシックページは Copilot を支えるコンテンツ形式に十分に含まれず、応答の網羅性と精度を下げる」と初めて明記した。Copilot の回答品質の議論に、コンテンツ基盤の近代化が入る。

**詳細** SharePoint Blog に 8/31 付で「Upcoming changes to classic experiences in SharePoint Online」（記事ID 4549091）が出て、一次の Learn 記事 `sharepoint/classic-user-created-page-deprecation`（`ms.date` 2026-08-24 / `updated_at` **2026-08-28T22:04Z**）が公開されている。全 digest に掲載歴はない。

- **フェーズ1（2027-03-01 開始）**: 全テナントでクラシック発行サイトの新規作成とクラシック発行機能の有効化が停止し、`AllowClassicPublishingSiteCreation` が `False` で固定される。⚠️ **同日以降に作成された新規テナントは追加で**クラシックページの新規作成が不可になり、custom script の追加・更新が既定で無効・`DenyAddAndCustomizePages` が `True` で固定される
- **フェーズ2（2028-10-01 開始）**: 上記の制限が既存の全テナントへ広がり、クラシックのユーザー作成ページが読み取り専用になる
- **対象**: wiki ページ / Web パーツページ / ブログページ / 発行ページ / SharePoint Designer・サードパーティ製の カスタム ASPX ページ。リストとライブラリのビュー、リストフォームページは今回の範囲外だが、そこに埋め込まれた custom script は対象
- **対象クラウド**: GCC / GCC High / DoD、エアギャップ環境、21Vianet 運用版を含む全環境
- **止まらないもの**: Microsoft がコンテンツを削除・変更することはなく、既存ページは閲覧可能なまま残る。モダンページと SPFx 製のカスタムソリューションは影響を受けない

管理者が本日から着手できる作業は棚卸しである。Purview 監査の **SharePoint Classic Activities** カテゴリ（Audit Standard に含まれ全組織が使える）の `ClassicPageCreated` / `ClassicPageEdited` / `ClassicPageViewed` イベントで実利用を特定し、Microsoft 365 Assessment Tool で近代化の可否を評価する。移行には PnP PowerShell の変換ガイダンスと **SharePoint Page Migration Agent（Preview）** があるが、⚠️ **後者はオープンソースで Microsoft のサポート SLA がなく**、高度にカスタマイズされたページは再設計か手作業での作り直しが必要になるとされている。ブログ側は対象機能の利用が月間アクティブテナントの **5%未満**だとしている。フェーズ1では10種類の発行系サイトテンプレート（`BLANKINTERNETCONTAINER#0`・`CMSPUBLISHING#0`・`ENTERWIKI#0` 等）の新規作成が塞がるため、SharePoint Server からの as-is 移行も同日以降は成立しない。

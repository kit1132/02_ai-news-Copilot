### 1. Cowork のアクセスを決めているのはスペンディングポリシーだけだった — 少額上限で使わせない運用は成立しない

**要点**: 管理者が Cowork のアクセスを制御できるのは、Cowork を選択したスペンディングポリシーの適用範囲だけだと一次が明記した。上限1クレジットのテナント全体ポリシーでも全社にアクセスが開くため、上限を絞って実質的に止める運用は前提から崩れる。

**詳細**: `microsoft-365/copilot/cowork/cowork-access`「Determine access controls for Copilot Cowork」が本日の巡回ではじめて把握できた（`ms.date` **2026-08-21**・ページ表記の Last updated は **2026-09-08**。⚠️ **全 digest で掲載歴ゼロ**）。同ページは判定順序を5段で規定する。

- スペンディングポリシーの適用範囲: これがアクセス付与そのものにあたる。M365 管理センターの Copilot > Cost Management > Configuration で、ユーザーを直接（All users）または セキュリティグループ経由で含み、かつ Select agents and services で Cowork を選んでいるポリシーが1つでもあればアクセスがある。1つも無ければアクセスは無い
- ディスカバリー設定: 可視性だけを制御し、アクセスは制御しない。⚠️ **ポリシーに含まれるユーザーはディスカバリーが無効でもアクセスできる**
- 複数ポリシーの重複: より制限的なポリシーが優先されることはない。優先順位（ユーザー単位上限が最大 → ポリシー全体の上限が最大 → 作成が最新）が決めるのは適用される上限だけで、アクセスの可否ではない
- テナントのモデル設定: 表示されるモデルを制御するだけで、アクセスには影響しない。Anthropic ファミリーを無効化してもアクセスは残り、Auto は残るモデルから選ぶ。この設定はテナント全体で、一部ユーザーへの限定はできない
- クレジット上限への到達: 上限は支出の安全装置であって実時間のアクセスゲートではない。⚠️ **消費と上限の評価は非同期のため、上限到達後もタスクを開始できることがある**

掲載されている想定例が要点を示す。パイロットグループに 5,000クレジット、All users に1クレジットの2ポリシーを置くと、**テナント全員が Cowork を使える**——1クレジットのポリシーはテナント全体へのアクセス付与であって、大多数を締め出す手段ではない。パイロット限定にするなら、全社ポリシーから Cowork を外すか、パイロット以外をどのポリシーにも含めない。あわせて `cowork-admin-governance`（`ms.date` **2026-08-28 → 2026-09-10**）が、Frontier / Preview 期のエージェントベースのアクセス制御を**非推奨**と明記した。管理センターの Agents > All Agents に Cowork の項目は残るが、そこでの構成はアクセスに影響しない。旧の許可リストをポリシーへ移す手順（Entra ID のセキュリティグループ化 → Cost Management で Specific groups を選択 → Select agents and services で Cowork を選択）も同ページに追加されている。

### 2. Cowork の通信は Power Apps 基盤を通る — Power Apps 未導入テナントは許可リストに無いまま使わせている

**要点**: Cowork のサービス通信が `*.gateway.prod.island.powerapps.com:443` に集約されると一次が公開した。Power Apps を使っていないテナントではこのホストが許可リストに無く、SSL/TLS 検査や絶対寿命タイムアウトを掛けているとタスクが止まる側に回る。

**詳細**: `microsoft-365/copilot/cowork/cowork-network-endpoints`「Cowork network endpoints」（`ms.date` **2026-09-04**）も本日はじめて把握できたページで、⚠️ **全 digest で掲載歴ゼロ**である。要件は4系統に分かれる。

- サービスエンドポイント: ルーティングサービスとリージョンランタイムの両方が `*.gateway.prod.island.powerapps.com` の443。ルーティングはユーザーごとに動的に決まりクラスター識別子も変わるため、**個別のリージョンサブドメインに固定しない**。⚠️ **ページ自身が「これらは Power Apps インフラの一部で、Power Apps を使っていない組織では既存の許可リストに無いかもしれない」と書いている**。IP ベースが必要な場合は Azure のサービスタグ `PowerPlatformInfra` を参照する（週次更新・新レンジは利用開始の1週間以上前に掲載される）
- SSL/TLS 検査: 当該ホストへの通信では**非対応**。復号・検査・再暗号化を挟むと長時間の SSE 接続が切れ、メッセージ配信失敗・リトライ・タスクの停止につながる
- 長時間接続: `/v1/subscribe` と `/v1/mru/subscribe` はタイムアウト無し、または最低30分が必要。⚠️ **アイドルタイムアウトではなく絶対寿命タイムアウトを課すプロキシは、通信が流れていても切断する**（サーバー側のキープアライブでは回避できない）ため、当該ホストを絶対寿命の対象から除外する
- 条件付きアクセス: 全サービス要求のトークン対象は単一アプリ `6ab48b67-cd74-4ad4-81af-5932984589be`（Weave / M365 Host App）。条件付きアクセスがこれをブロックしていないこと、サービスプリンシパルがトークンを取得できること、必要スコープの On-Behalf-Of 同意が済んでいることを確認する

標準依存として `copilot.cloud.microsoft` / `login.microsoftonline.com` / `graph.microsoft.com` の443も挙がるが、これらは M365 利用テナントなら通常すでに許可されている。UX の入口は `copilot.cloud.microsoft/chat` と `m365.cloud.microsoft/chat/agent/<agent-id>.weave` の2本である。

- https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-network-endpoints
